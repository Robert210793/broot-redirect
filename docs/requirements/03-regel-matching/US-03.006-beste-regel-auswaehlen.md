# US-03.006: Beste passende Regel auswählen

> **Bestandsaufnahme:** Nachträglich aus dem Code abgeleitet (Stand 2026-10-24). Dokumentiert das Ist-Verhalten. `[x]` = durch automatisierte Tests belegt, `[ ]` = umgesetzt, aber ohne automatisierten Test. Keine fachliche Freigabe, keine Abnahme.

**Als** Administrator
**möchte ich**, dass bei mehreren passenden Regeln immer die spezifischste gewählt wird
**damit** allgemeine und spezielle Regeln nebeneinander existieren können und das Ergebnis vorhersehbar bleibt

## Akzeptanzkriterien

- [x] Regeln vom Typ «Wildcard» werden zuerst geprüft und gewinnen gegenüber «Teilweise»
- [ ] Die Prüfung endet beim ersten Treffer einer Stufe: zuerst «Wildcard», dann «Teilweise» und «Domain», zuletzt «Regex»
- [x] Innerhalb der Stufe «Teilweise/Domain» gewinnt der höhere Score
- [x] Bei gleichem Score entscheidet in dieser Reihenfolge: mehr statische Segmente, mehr Query-Paare, weniger Wildcard-Segmente, längerer Matcher, älteres Erstelldatum, kleinere Regel-ID
- [x] Der längere Matcher gewinnt nicht gegen einen bereits exakten Treffer
- [x] Bei gleicher Ausgangslage ist der Sieger immer derselbe (deterministisch)
- [x] Greift keine Regel, liefert das Matching kein Ergebnis

## Hinweise

- Der Score dient nur der Auswahl; dem Benutzer wird die Qualität angezeigt (siehe US-03.007).
- Alle Lesezugriffe erfolgen aus dem In-Memory-Cache, nicht aus dem Storage.
- Belegende Tests: `RuleMatchingServiceTests`.
