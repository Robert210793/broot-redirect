# US-11.006: Anfragen pro IP begrenzen

> **Bestandsaufnahme:** Nachträglich aus dem Code abgeleitet (Stand 2026-10-24). Dokumentiert das Ist-Verhalten. `[x]` = durch automatisierte Tests belegt, `[ ]` = umgesetzt, aber ohne automatisierten Test. Keine fachliche Freigabe, keine Abnahme.

**Als** Betreiber
**möchte ich** die Anzahl API-Anfragen pro IP und Zeitfenster begrenzen
**damit** einzelne Clients die Anwendung nicht überlasten oder das Tracking fluten können

## Akzeptanzkriterien

- [x] Anfragen unter `/api/` werden pro IP in einem festen Zeitfenster gezählt; Pfade ausserhalb von `/api/` sind ausgenommen
- [x] Es gelten drei getrennt gezählte Stufen: Tracking (Erfassen, Feedback), Admin (Regeln, globale Regeln, Statistiken, Ändern der Einstellungen) und alle übrigen API-Anfragen
- [x] Jede Antwort trägt Kopfzeilen mit Limit, verbleibenden Anfragen und Zeitpunkt des Zurücksetzens
- [x] Bei Überschreitung antwortet die API mit 429, einer JSON-Meldung und der Kopfzeile `Retry-After`
- [x] Unterschiedliche IPs werden unabhängig gezählt; nach Ablauf des Fensters beginnt die Zählung neu; abgelaufene Zähler werden aufgeräumt
- [ ] Ohne Konfiguration gelten 300 Anfragen pro Minute für Tracking und übrige Anfragen, 60 pro Minute für Admin-Anfragen

## Hinweise

- Die Zähler liegen nur im Arbeitsspeicher; sie werden bei einem Neustart zurückgesetzt und nicht zwischen Instanzen geteilt.
- Belegende Tests: `RateLimitMiddlewareTests`.

## Offene Fragen

- [ ] **F1 · Client-IP hinter dem Azure-Ingress:** Die Weiterleitungs-Kopfzeilen (`X-Forwarded-For`) werden ausgewertet, aber ohne freigegebene Proxy-Netze. ASP.NET Core vertraut dann nur Proxies auf `localhost`. Hinter dem Ingress von Azure Container Apps bzw. App Service erkennen Begrenzung und Fehlversuch-Sperre deshalb voraussichtlich für alle Clients die IP des Ingress. Folgen: Alle Benutzer teilen sich ein Limit (300 Anfragen pro Minute bei rund drei API-Anfragen pro Aufruf der Info-Seite), und fünf Fehlversuche eines Angreifers sperren alle Administratoren aus. Vor der Entscheidung in der Produktivumgebung prüfen, welche IP protokolliert wird.
  - Option A: Netz des Ingress als vertrauenswürdig freigeben (bzw. die Liste bekannter Proxies leeren, wenn ausschliesslich der Ingress die Anwendung erreicht) — ✅ echte Client-IPs für Begrenzung und Sperre / ❌ bei direkter Erreichbarkeit unter Umgehung des Ingress liesse sich die IP fälschen
  - Option B: Begrenzung und Sperre beim Ingress bzw. in einer vorgelagerten WAF umsetzen — ✅ Schutz vor der Anwendung / ❌ zusätzliche Infrastruktur und Kosten
  - **Empfehlung:** Option A, weil die Anwendung als einzelner Container hinter dem Ingress betrieben wird und die bestehende Logik damit ohne neue Infrastruktur korrekt arbeitet.
