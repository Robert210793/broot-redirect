# US-11.007: Schreibende API-Anfragen gegen CSRF schützen

> **Bestandsaufnahme:** Nachträglich aus dem Code abgeleitet (Stand 2026-10-24). Dokumentiert das Ist-Verhalten. `[x]` = durch automatisierte Tests belegt, `[ ]` = umgesetzt, aber ohne automatisierten Test. Keine fachliche Freigabe, keine Abnahme.

**Als** Betreiber
**möchte ich**, dass schreibende API-Anfragen nur von der eigenen Anwendung angenommen werden
**damit** eine fremde Webseite eine angemeldete Admin-Session nicht für Änderungen missbrauchen kann

## Akzeptanzkriterien

- [x] Lesende Anfragen (GET, HEAD, OPTIONS) und Pfade ausserhalb von `/api/` werden nicht geprüft
- [x] Bei schreibenden Anfragen (POST, PUT, DELETE) muss der `Origin` zum Host der Anfrage passen; fehlt er, muss der `Referer` passen
- [x] Fehlen beide, sind sie ungültig oder passen sie nicht, wird die Anfrage mit 403 abgewiesen

## Hinweise

- Es gibt kein CSRF-Token; der Schutz funktioniert, weil das Admin-Panel von derselben Herkunft ausgeliefert wird. Skripte und Werkzeuge wie curl müssen für schreibende Anfragen einen passenden `Origin` mitsenden.
- Belegende Tests: `CsrfProtectionMiddlewareTests`.
