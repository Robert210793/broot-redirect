# US-13.001: Regeln aus QM Pro beim Publizieren schreiben und beim Zurückziehen deaktivieren

**Als** Administrator der Weiterleitung
**möchte ich**, dass QM Pro 365 beim Publizieren eines Dokuments die Weiterleitungsregel selbst schreibt und beim Zurückziehen deaktiviert
**damit** alte Links auf die On-Premises-SharePoint-Ablage ohne manuelle Regelpflege auf die aktuelle Fassung in der Publikationsbibliothek zeigen

## Akzeptanzkriterien

### Publizieren

- [x] Ein Endpunkt für das Publizieren nimmt die Dokument-ID, die alte On-Premises-URL und die Publikations-URL eines Dokuments entgegen
- [x] Existiert zur Dokument-ID noch keine Regel, wird eine Regel vom Typ «Wildcard (exakter Pfad)» angelegt: Matcher = Pfad der alten URL inklusive Query (der Host wird verworfen), Ziel-URL = Publikations-URL, Auto-Weiterleitung aus, Herkunft «QM Pro», aktiv
- [x] Existiert zur Dokument-ID bereits eine Regel, werden Matcher und Ziel-URL überschrieben und die Regel wird aktiviert; Regel-ID und Erstelldatum bleiben erhalten
- [x] Die Herkunft einer Regel kennt neben «Manuell», «Import» und «Unbekannt» den neuen Wert «QM Pro»; nur über die QM-Pro-Schnittstelle angelegte Regeln erhalten ihn
- [x] Ein wiederholter Aufruf mit unveränderten Daten für eine aktive Regel verändert die Regel nicht
- [x] Die alte URL wird als Pfad ohne Host (beginnend mit `/`, z. B. `/ims/Strategie/Merkblatt%20IMS.docx`) oder als absolute URL angenommen; bei einer absoluten URL wird der Host verworfen
- [x] Fehlen Dokument-ID, alte URL oder Publikations-URL, ist die alte URL weder Pfad noch absolute URL oder ist die Publikations-URL keine gültige absolute URL, antwortet der Endpunkt mit 400 und einer Fehlermeldung
- [x] Ist die alte URL bereits Matcher einer anderen Regel (aktiv oder deaktiviert), wird der Aufruf mit 409 abgewiesen und die bestehende Regel bleibt unverändert
- [x] ~~Überlappt die alte URL hierarchisch mit einer bestehenden Regel vom Typ «Teilweise», wird der Aufruf wie in der Regelverwaltung mit 409 und dem Code `MATCHER_CONFLICT` abgewiesen~~ Liegt die alte URL unter einer Regel vom Typ «Teilweise» (z. B. einem Bereichsordner), wird die Regel angelegt; beide Regeln bestehen nebeneinander (Korrektur K3 in [US-13.003](US-13.003-bereichsregeln-abgleichen.md), 2026-10-29)

### Zurückziehen

- [x] Ein Endpunkt für das Zurückziehen nimmt die Dokument-ID entgegen und deaktiviert die Regel des Dokuments
- [x] Eine deaktivierte Regel wird weder bei der Weiterleitung noch auf der Info-Seite noch in der Validierung berücksichtigt
- [x] Das Zurückziehen einer bereits deaktivierten Regel ist ohne Fehler möglich und lässt die Regel deaktiviert
- [x] Existiert zur Dokument-ID keine Regel, antwortet der Endpunkt mit Erfolg und verändert nichts
- [x] Ein erneutes Publizieren derselben Dokument-ID aktiviert die deaktivierte Regel wieder

### Zugriffsschutz

- [x] Beide Endpunkte verlangen einen API-Key im Request-Header; der erwartete Key stammt aus der Startkonfiguration (Umgebungsvariable)
- [x] Fehlt der API-Key oder ist er falsch, antworten die Endpunkte mit 401 und schreiben nichts
- [x] Ist kein API-Key konfiguriert, werden alle Aufrufe der Endpunkte abgewiesen
- [x] Die Endpunkte sind ohne Admin-Session und ohne Origin- bzw. Referer-Header aufrufbar; alle übrigen Admin-Endpunkte bleiben unverändert geschützt

### Admin-Panel

- [ ] Regeln aus QM Pro erscheinen in der Regelliste mit der Herkunft «QM Pro»
- [ ] Deaktivierte Regeln sind in der Regelliste als deaktiviert erkennbar
- [x] Regeln aus QM Pro lassen sich im Admin-Panel nicht bearbeiten
- [x] Regeln aus QM Pro lassen sich im Admin-Panel einzeln, mehrfach und über «Alle Regeln löschen» löschen

### Import und Export

- [x] Wird ein Import-Eintrag über ID oder Matcher einer Regel aus QM Pro zugeordnet, wird er übersprungen, als Fehler gemeldet und die Regel bleibt unverändert
- [x] Der Export enthält in allen Formaten (JSON, CSV, XLSX) zusätzlich Herkunft und Status jeder Regel
- [x] Ein Import-Eintrag mit Herkunft «QM Pro» wird übersprungen und als Fehler gemeldet, auch wenn keine passende Regel existiert

### Erstbefüllung (Nachtrag 2026-10-29, Umsetzung in QM Pro)

- [x] Eine manuell auszulösende Admin-Funktion in QM Pro legt für alle bereits veröffentlichten migrierten Dokumente die Regel in broot-redirect an, ohne die Dokumente neu zu veröffentlichen
- [x] Pro Dokument werden dieselbe Dokument-ID, dieselbe alte URL und dieselbe Publikations-URL übermittelt wie beim Publizieren; ein späteres Publizieren aktualisiert die Regel, ein Zurückziehen deaktiviert sie
- [x] Dokumente ohne Kopie in der Publikationsbibliothek und Dokumente mit mehr als einer Kopie werden übersprungen und ausgewiesen
- [x] Ein Testlauf übermittelt nichts und zeigt pro Dokument alte URL und Publikations-URL, die übermittelt würden
- [x] Das Ergebnis enthält die Anzahl angelegter, aktualisierter, unveränderter, kollidierender, fehlgeschlagener und übersprungener Dokumente sowie pro Dokument Ergebnis und Fehler; ein erneuter Aufruf ist unbedenklich

## Hinweise

- **Kontext:** Das On-Premises-SharePoint des Kunden ist abgelöst; seine Hostnamen sind per DNS bereits auf diese Applikation umgeleitet. Die alte URL eines Dokuments ist in der Administrationsbibliothek von QM Pro hinterlegt, das Ziel ist die URL der publizierten Kopie in der Publikationsbibliothek. Pro Dokument gibt es genau eine alte URL und genau eine Publikations-URL. Alte URLs stammen ausschliesslich aus der Migration; neue Dokumente haben keine alte URL und erzeugen keine Regel.
- **Dokument-ID:** QM Pro identifiziert ein Dokument über `brtqmSourceId` im Format `SiteUrl|ListGuid|ItemUniqueId` (z. B. `https://tenant.sharepoint.com/sites/QM|bfcdf1ce-…|3f2a…`). Der Wert enthält `/` und `|`; die Form der Übergabe (Pfad, Query oder Body) ist im Refinement festzulegen.
- **Auslöser in QM Pro:** Publizieren erfolgt in `brtqmDocumentPublish`. Zurückziehen erfolgt in `brtqmDocumentUnpublish` und wird durch Löschen, Inaktivieren und Archivieren eines Dokuments ausgelöst. Beim Zurückziehen steht QM Pro nur noch die Dokument-ID zur Verfügung, weil das Dokument bereits gelöscht sein kann. Ein Reaktivieren löst in QM Pro ein erneutes Publizieren aus.
- **Publikations-URL ändert sich:** Wird ein Dokument verschoben, umbenannt oder als PDF publiziert, ändert sich die Publikations-URL. Jedes Publizieren überträgt deshalb die aktuelle URL.
- **Ausgangslage:** Die QM-Pro-Regeln werden von Grund auf neu aufgebaut. Eine Übernahme bestehender manueller oder importierter Regeln ist nicht vorgesehen.
- **Abgrenzung:** Die Umsetzung auf Seite QM Pro (Feld für die alte URL in der Administrationsbibliothek, Konfiguration von Adresse und API-Key, Aufrufe in Publish und Unpublish) ist nicht Teil dieser Story und folgt separat im Repository `broot-spo-qms-backend-ps`.
- **Erstbefüllung (Nachtrag):** Der Import von broot-redirect übernimmt keine Dokument-ID und überspringt Einträge mit Herkunft «QM Pro» (F3). Bereits veröffentlichte Dokumente erhalten ihre Regel deshalb über die Admin-Funktion `brtqmRedirectRulesInitialize` in `broot-spo-qms-backend-ps` (Branch `feature/broot-redirect-integration`), die pro Dokument den Publizieren-Endpunkt aufruft. Die Dokument-ID stammt aus Site-URL, Listen-GUID und `UniqueId` des Eintrags der Administrationsbibliothek, die Kopie wird über `brtqmSourceId` gefunden. Ohne Änderung in broot-redirect; die Pilotphase umfasst rund 165 Dokumente, ein Lauf benötigt keine Aufteilung. Vorher dürfen keine importierten Regeln mit denselben alten URLs bestehen, sonst endet der Aufruf für diese Dokumente mit 409.
- Das manuelle Aktivieren und Deaktivieren von Regeln im Admin-Panel ist nicht Teil dieser Story.
- Die neuen Endpunkte dürfen nicht unter einem Präfix liegen, das die `AdminSessionMiddleware` als geschützt behandelt (`/api/rules` usw.). Sie fallen damit in das globale Limit der Anfragebegrenzung (siehe US-11.006); ein Massen-Publizieren über `brtqmDocumentPublishAll` kann viele Aufrufe in kurzer Zeit erzeugen.
- **Mengengerüst:** Geschätzt über 1000 Dokumente mit alter URL. Ein Massen-Publizieren erzeugt entsprechend viele Aufrufe in kurzer Folge; die Info-Seite darf dadurch nicht durch die Anfragebegrenzung blockiert werden.

## Technische Umsetzung

### API
- Neuer Controller für das Präfix `/api/qm-pro` mit `POST /api/qm-pro/publish` (Body `{ documentId, oldUrl, publicationUrl }`) und `POST /api/qm-pro/unpublish` (Body `{ documentId }`); die Dokument-ID steht nur im Body
- API-Key-Prüfung als Autorisierungsfilter am Controller: Header `X-Api-Key`, erwarteter Wert aus `SmartRedirect__QmProApiKey`, laufzeitkonstanter Vergleich der SHA-256-Hashes; falscher, fehlender oder nicht konfigurierter Key ergibt 401 ohne Schreibzugriff; der Key wird nie geloggt
- CSRF-Schutz nimmt das Segment `/api/qm-pro` aus; die Session-Autorisierung bleibt unverändert, `/api/qm-pro` wird nicht in die geschützten Präfixe aufgenommen; Regressionstests sichern die bestehenden Präfixe
- Anfragebegrenzung erhält eine eigene Stufe `Integration` für `/api/qm-pro/*` mit konfigurierbarem Limit `SmartRedirect__RateLimitIntegrationMax` (Standard 1200 pro Minute)
- Antworten: Publizieren 201 `created`, 200 `updated` (auch Reaktivierung) oder 200 `unchanged`; Zurückziehen 200 `deactivated`, `alreadyInactive` oder `notFound`; jeweils `{ ruleId, result }`. Fehler: 400 `VALIDATION_ERROR`, 401, 409 `MATCHER_DUPLICATE` mit konfliktierender Regel (409 `MATCHER_CONFLICT` entfällt seit K3 in US-13.003), 429, 503 mit `Retry-After`, solange der Cache nicht aufgewärmt ist
- Bearbeiten (`PUT /api/rules/{id}`) einer Regel mit Herkunft «QM Pro» wird mit 409 `RULE_MANAGED_BY_QMPRO` abgewiesen; Löschen bleibt erlaubt
- «Alle Regeln löschen» lädt den Cache am Jobende aus dem Storage neu, statt ihn zu leeren
- Import (Vorschau und Ausführung) überspringt Einträge mit Fehler, die einer QM-Pro-Regel zugeordnet werden oder selbst die Herkunft «QM Pro» tragen
- Export: CSV und XLSX erhalten die Spalten `Origin` (`manual|import|unknown|qmpro`) und `Status` (`active|inactive`); JSON enthält Herkunft, Status und Dokument-ID; beim Import wird `Status` ignoriert

### Core
- Weiterleitungsregel erhält die externe Dokument-ID und den Aktiv-Status (Standard aktiv); die Herkunft erhält den Wert «QM Pro»
- Regel-Cache erhält einen Lookup per Dokument-ID und eine Prüfung auf gleichwertige Matcher (dekodierte Segmente ohne Gross-/Kleinschreibung, Query als Menge von Schlüssel/Wert-Paaren) über alle Regeln, auch deaktivierte
- Matching-Logik bleibt unverändert

### Infrastructure
- Regel-Entity erhält die Spalten für Dokument-ID und Aktiv-Status (nullable, fehlend = aktiv); die Herkunft `qmpro` wird gemappt
- Cache-Aufbau lässt deaktivierte Regeln in den Matching-Indexen aus, behält sie in der Gesamtliste und im Matcher-Index und baut zusätzlich einen Index Dokument-ID → Regel auf; doppelte Dokument-IDs beim Warmup werden geloggt

### Client
- Regelmodell um Herkunft «QM Pro», Aktiv-Status und Dokument-ID ergänzen
- Regelliste: Herkunft «QM Pro» als Badge, deaktivierte Regeln mit Badge «deaktiviert» und abgeschwächter Zeile, Bearbeiten für QM-Pro-Regeln deaktiviert mit Hinweis «Regel wird von QM Pro verwaltet»; Auswahl und Löschen bleiben möglich
- Regel-Dialog zeigt QM-Pro-Regeln nur lesend
- Keine neue Route

### Dokumentation
- `README.md`, Kapitel 2, 5, 7, 8, 9, 10, 12 und 15 (inklusive Empfehlung für den API-Key: mindestens 32 Zufallsbytes)

## Technisches Refinement

### Neue Komponenten
- `Broot.Redirect.API.Controllers.QmProController` — Endpunkte Publizieren und Zurückziehen, übersetzt Ergebnisse in HTTP-Antworten, 503 vor dem Warmup
- `Broot.Redirect.API.Services.QmProRuleService` (Singleton) — Validierung, Bildung des Matchers aus der alten URL (Pfad und Query ohne Host und Fragment, kanonisiert wie beim Import), Prüfung als Wildcard-Regel, Lookup per Dokument-ID, Duplikat- und Überlappungsprüfung, Idempotenzvergleich, Schreiben «zuerst Storage, dann Cache», prozessweite Serialisierung
- `Broot.Redirect.API.Filters.QmProApiKeyFilter` — API-Key-Prüfung
- `Broot.Redirect.API.Dtos.QmProDtos` — `QmProPublishRequest`, `QmProUnpublishRequest`, `QmProRuleResponse`

### Geänderte Komponenten
- Core: `RedirectRule` (`ExternalDocumentId`, `IsActive`), `RuleSource` (`QmPro`), `IRuleCacheService` (`GetByExternalDocumentId`, `FindEquivalentMatcher`)
- Infrastructure: `RedirectRuleEntity`, `RuleCacheService`
- API: `BrootRedirectOptions` (`QmProApiKey`, `RateLimitIntegrationMax`), `CsrfProtectionMiddleware`, `RateLimitMiddleware`, `RulesController` (Update, DeleteAll, Import, ImportPreview), `RuleImportExportService` und `ImportRuleEntry` (Herkunft, Status), `Program.cs` (Filter, Startwarnung ohne Key)
- Client: `redirect-rule.ts`, `RulesListComponent`, `RuleModalComponent`
- Tests: Unit-Tests für Service, Filter, Middlewares, Cache-Indexe, Entity-Mapping (Altzeile ohne neue Spalten ergibt aktiv), Import/Export und Bearbeitungssperre; Azurite-Integrationstest mit Altzeile

### Externe Datenzugriffe
- Lesen: ausschliesslich aus dem Cache; Table Storage nur beim Warmup
- Schreiben: Tabelle `RedirectRules` über die bestehenden Repository-Methoden (Anlegen, Aktualisieren); Zurückziehen ist ein Update mit `IsActive=false`; keine neue Tabelle, keine Migration
- Eingehend: QM Pro 365 (`brtqmDocumentPublish`, `brtqmDocumentUnpublish`, `brtqmDocumentPublishAll`) per HTTPS mit `X-Api-Key`

### Messaging
- Queue: keine. Aufrufe sind synchron und idempotent; Wiederholungen bei 429, 503 oder 5xx übernimmt QM Pro

### Entschiedene Tradeoffs
- **Entscheidung:** Präfix `/api/qm-pro`, `POST …/publish` und `POST …/unpublish`, Dokument-ID im JSON-Body. **Begründung:** `brtqmSourceId` enthält `/` und `|`; im Pfad bräuchte es Doppelkodierung, in der Query drohen Kodierfehler auf PowerShell-Seite. POST statt DELETE mit Body, weil Proxys DELETE mit Body uneinheitlich behandeln. *(Grundlage: ADR-001)*
- **Entscheidung:** Header `X-Api-Key`, Schlüssel `SmartRedirect__QmProApiKey`, Hash-Vergleich mit `FixedTimeEquals`, 401 ohne Unterscheidung der Ursache, keine Brute-Force-Sperre. **Begründung:** Gleiches Muster wie beim Admin-Passwort; ein Key mit hoher Entropie plus Anfragebegrenzung genügt. Managed Identity wurde vom PO als zu aufwendig verworfen. *(Grundlage: ADR-001)*
- **Entscheidung:** Ausnahme aus dem CSRF-Schutz, keine Änderung an der Session-Autorisierung. **Begründung:** CSRF betrifft nur automatisch mitgesendete Cookies; einen eigenen Header sendet der Browser nicht automatisch. *(Grundlage: ADR-001)*
- **Entscheidung:** Eigene Stufe `Integration` der Anfragebegrenzung, Standard 1200 pro Minute. **Begründung:** Hinter dem Ingress teilen sich womöglich alle Clients eine IP; ein PublishAll mit über 1000 Dokumenten würde sonst das globale Kontingent der Info-Seite erschöpfen. *(billig umkehrbar, Konfiguration)*
- **Entscheidung:** `ExternalDocumentId` und `IsActive` direkt auf der Regel; im Storage `bool?` mit «null = aktiv». **Begründung:** Rückwärtskompatibel ohne Migration; eine separate Zuordnungstabelle hätte keine Transaktion mit der Regeltabelle. *(Grundlage: ADR-002)*
- **Entscheidung:** Lookup per Dokument-ID über einen Cache-Index ohne Beachtung der Gross-/Kleinschreibung. **Begründung:** O(1) gemäss «Lesen aus dem Cache». *(billig umkehrbar)*
- **Entscheidung:** Deaktivierte Regeln fehlen in den Matching-Indexen, bleiben aber in Gesamtliste, Matcher-Index sowie Duplikat- und Überlappungsprüfung. **Begründung:** Weiterleitung, Info-Seite und Validierung laufen über dieselben Indexe; eine Stelle, keine Kosten im Matching-Pfad; 409 auch gegen deaktivierte Regeln (F5). *(Grundlage: ADR-002)*
- **Entscheidung:** Neue Prüfung auf gleichwertige Matcher (409 `MATCHER_DUPLICATE`) vor der bestehenden Überlappungsprüfung (409 `MATCHER_CONFLICT`). **Begründung:** Die bestehende Duplikatprüfung vergleicht ordinal; `/a b` und `/a%20b` würden nicht erkannt. Gleicher Pfad mit anderer Query bleibt erlaubt. Die Admin-Endpunkte bleiben unverändert. *(billig umkehrbar)*
- **Entscheidung:** Idempotenz: Eine aktive Regel mit gleichem kanonischem Matcher und gleicher Ziel-URL wird nicht geschrieben; sonst werden Matcher, Ziel-URL und Aktiv-Status gesetzt, ID, Erstelldatum und Herkunft bleiben. **Begründung:** Kein Schreibvorgang und kein Index-Neuaufbau bei unveränderten Daten, relevant bei PublishAll. *(Akzeptanzkriterien)*
- **Entscheidung:** Statuscodes wie unter «Technische Umsetzung»; Zurückziehen antwortet immer mit 200, auch bei `notFound`; 503 vor dem Warmup. **Begründung:** QM Pro protokolliert Ergebnisse ohne Sonderfälle (F1); 503 verhindert doppelte Regeln bei leerem Cache. *(Grundlage: ADR-001)*
- **Entscheidung:** Exportspalten `Origin` (Alias `Herkunft`) und `Status`; der Import erkennt QM-Pro-Regeln über ID, kanonischen Matcher oder `Origin = qmpro`. **Begründung:** Das Alias `Source` ist bereits dem Matcher zugeordnet. *(F3/F6, billig umkehrbar)*
- **Entscheidung:** Bearbeitungssperre in Client und Server; der Server antwortet mit 409 statt 403. **Begründung:** Der Client behandelt 403 als fehlende Anmeldung und leitet auf die Anmeldeseite um. *(billig umkehrbar)*
- **Entscheidung:** Kein Distributed Lock; Publizieren und Zurückziehen werden prozessweit über eine `SemaphoreSlim(1,1)` serialisiert. **Begründung:** Single-Instance; ein globaler Lock ist nötig, weil Matcher-Konflikte dokumentübergreifend sind; der Durchsatz reicht (10–50 ms pro Schreibvorgang). Restrisiko wie heute: parallele Admin-Schreibvorgänge oder Import-Jobs sind nicht einbezogen. *(CLAUDE.md, Goldene Regel 4)*
- **Entscheidung:** «Alle Regeln löschen» lädt den Cache am Jobende aus dem Storage neu. **Begründung:** Während des Jobs angelegte Regeln (paralleles PublishAll) gingen im Cache sonst verloren und würden beim nächsten Publizieren dupliziert. *(billig umkehrbar)*
